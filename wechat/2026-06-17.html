安全、AI、底层，三大拐点显现

今天的信号覆盖多个维度，从隐私攻防到内存安全，从AI热潮到底层优化，值得技术人逐一审视。

━ 1 ━ 你的系统可能正在裸奔

从Chrome广告拦截器即将终结、苹果削弱隐私功能，到LinkedIn招聘后门，再到GrapheneOS的积极防御和JWT安全争论，多个信号表明隐私与安全防线正面临前后夹击。用户的数据保护和开发者的认证策略都需要重新审视。

▸ GrapheneOS移植至Android 17

GrapheneOS已成功移植到Android 17，官方稳定版即将发布。 这表明GrapheneOS能跟上最新安卓版本，为用户提供更强的安全性和隐私保护。 移植工作已完成，但官方发布仍需时间，社区讨论了设备兼容性及与原生系统的差异。

▸ 苹果更改规则可能使Hide My Email功能失效

苹果计划将Hide My Email和Sign in with Apple生成的别名统一归于@private.icloud.com子域名下，这使得网站可以轻松屏蔽所有该子域的邮件地址。 这一变化可能严重削弱Hide My Email的隐私保护作用，因为越来越多的网站可能选择屏蔽这些“隐私友好”的邮箱地址，导致用户无法注册或接收重要邮件。 目前Hide My Email别名使用@icloud.com域名，而Sign in with Apple使用@private.icloud.com，合并后两者都使用@private.icloud.com，网站可针对性屏蔽。用户若未预先生成大量别名，后续可能受限于新规则。

▸ Chrome更新将终结广告拦截器，Manifest V3成关键

Google Chrome即将推出的更新强制要求所有扩展程序迁移到Manifest V3，这将导致uBlock Origin等流行广告拦截器因核心功能受限而无法正常工作。 此举将影响数以百万计依赖广告拦截器的用户，并可能重塑浏览器扩展生态，同时引发对浏览器厂商在隐私与广告收入之间平衡的广泛讨论。 Manifest V3引入了新的declarativeNetRequest API，取代了Manifest V2中强大的webRequest API，从而将过滤规则数量限制在约30万条以内，远低于uBlock Origin所需的数百万条。

▸ 停止在浏览器会话中使用JWT的争论

一篇题为“Stop Using JWTs”的Gist文章引发了社区关于在浏览器用户会话中使用JWT安全性的激烈讨论。文章及其引用的博客指出JWT在浏览器会话中存在无法撤销令牌、安全隐患等缺陷。 该讨论对Web开发者选择会话管理方案具有重要参考价值，因为JWT在浏览器中的不当使用可能导致安全漏洞，而社区反馈揭示了更均衡的技术选择视角。 讨论强调JWT在服务间通信中仍有价值，但在浏览器会话中需要谨慎。评论指出可以通过限制令牌生命周期（如5-15分钟）并配合刷新机制来解决部分问题，同时撤销列表可以比会话数据库更小。

▸ LinkedIn职位Offer暗藏后门攻击

安全研究人员发现，攻击者通过LinkedIn上的虚假职位Offer，诱导开发者下载并运行包含后门的GitHub仓库代码（一个npm项目），从而在开发者机器上执行恶意载荷。 该事件揭示了针对开发者的新型供应链攻击手段，威胁广泛使用LinkedIn求职的高技术人才，可能导致敏感数据泄露或系统被控。 攻击者发送的npm项目看起来是一个需要修复bug的小项目，但实际包含Node.js脚本，运行后会从远程服务器下载并执行恶意代码。

▸ 本地运行大模型是否已够好？社区存在争议

▸ SubQ 1.1 Small 发布：线性稀疏注意力实现 64 倍加速

SubQ 1.1 Small 引入了一种稀疏注意力机制（SSA），其计算复杂度随上下文长度线性增长。在处理 100 万 token 时，相比密集注意力机制，计算量减少了 64.5 倍，运行速度比 FlashAttention-2 快 56 倍。 这一突破显著降低了长上下文场景下的计算成本，可能推动大语言模型高效处理超长序列的实用化进程。它为注意力机制的效率优化提供了新方向，有望影响未来模型架构设计。 SSA 的核心是学习为每个查询选择少量关键值对进行计算，从而实现线性复杂度。然而，社区指出该技术报告缺乏架构细节和代码开源，RULER 基准测试也仅覆盖到 128k 上下文长度。

▸ 终端文本渲染的诸多缺陷（2024）

2024年，一篇技术博文详细列举了终端文本渲染中的多种问题，包括字形渲染、连字支持、性能等方面的不足。 该文对开发者尤为重要，因为终端是许多开发者的核心工具，渲染缺陷直接影响可读性和工作效率；同时文中指出的问题可能推动终端模拟器改进。 文章涵盖了从字体渲染管线到终端模拟器实现细节等多个层面的问题，例如不支持连字、反锯齿不佳、字形间距不正确等。

▸ RFC 10008 定义 HTTP QUERY 方法

RFC 10008 正式提出了一个新的 HTTP 方法 QUERY，用于执行安全和幂等的查询操作，并允许在请求体中携带查询内容。 该提案标准化了 API 查询操作，解决了传统上使用 GET（无请求体）或 POST（不保证安全幂等）的局限性，有望成为 Web API 设计的重要基础。 QUERY 方法结合了 GET 的安全/幂等语义与 POST 可携带请求体的能力；其核心定义在 HTTP 工作组的草案中，目前处于标准制定阶段。

▸ 巧用Bash内置/dev/tcp发送HTTP请求

一篇博客展示了在没有curl或wget的环境中，如何利用Bash的/dev/tcp文件描述符手动构造并发送HTTP请求。该方法在Docker内部容器等受限场景下尤为实用。 该技巧填补了轻量级环境下的网络调试空白，让开发者无需额外安装工具即可进行基本HTTP通信。同时它提醒人们理解底层网络协议的重要性，但也要警惕手工HTTP的脆弱性。 通过执行‘exec 3<>/dev/tcp/host/port’打开TCP连接，再用printf发送HTTP请求行和头部，最后用cat读取响应。需要注意的是，Bash的/dev/tcp仅提供TCP socket，而非HTTP解析库，因此不能正确处理分块编码、持久连接等高级特性，仅适合测试或简单交互。

▸ 《杀戮尖塔2》采用自定义PRNG确保种子跨平台一致

《杀戮尖塔2》开发团队在游戏中实现了自定义伪随机数生成器（PRNG），替代了C#标准库的随机函数，从而保证同一种子在不同平台上生成完全一致的随机序列。此前《杀戮尖塔1》因各平台标准库PRNG实现不同，导致种子不兼容。 这一改动确保了游戏种子的跨平台一致性，使玩家可以在不同设备上使用相同种子获得完全相同的游戏体验，同时避免因标准库更新导致的历史种子失效问题，对种子分享和竞速等社区活动具有重要意义。 文章指出，自定义PRNG不仅解决了平台差异，还避免了标准库未来版本变更带来的种子兼容性问题。此外，该实现可能使用了如PCG32等确定性算法，与Godot引擎自带RNG类（使用PCG32）类似。

▸ x86模拟器团队在运行时修补糟糕代码

x86模拟器团队在二进制翻译过程中发现原始x86-32代码存在严重性能问题，于是他们直接在模拟运行时修补了这些糟糕的代码片段，从而提升了执行效率。 这展示了模拟器开发中的一种巧妙工程实践，即利用二进制翻译的灵活性在运行时优化目标代码，这种思路对于提高模拟性能、处理遗留软件中不良编码习惯具有启发意义。 该模拟器采用二进制翻译技术，将x86-32指令视为字节码，模拟器相当于JIT编译器，动态生成宿主机器码。团队在翻译过程中识别出低效的代码模式并当场替换为更优化的翻译结果。

▸ 浮点除法有时比整数除法更快

一篇技术博客指出，在某些CPU架构和编译器优化条件下，浮点除法指令的执行效率可能超过整数除法。博主通过实验和性能分析展示了这一反直觉现象。 该发现挑战了“整数运算总是比浮点运算快”的普遍认知，为性能敏感型应用的优化提供了新思路。开发者可能需要重新评估在特定场景下使用浮点除法的成本收益。 现代CPU（如Intel Core系列）的浮点除法单元延迟常低于整数除法，且编译器可能将除以常数优化为乘以其倒数（使用双倍精度乘法），进一步提升浮点数除法的效率。然而，该优势依赖于具体的数据类型和编译器选项。
